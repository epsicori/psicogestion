**Reusa estos objetos en el formulario y en la Server Action. No escribas otros.**

### `lib/supabase/sesion.ts`

```ts
obtenerUsuario(): Promise<{ supabase, usuario: User | null }>
exigirSesion():   Promise<{ supabase, usuario: User }>   // redirige a /login si no hay
```

**`getUser()`, nunca `getSession()`.** `exigirSesion()` dentro de **cada** Server Action:
la autorización se comprueba dentro, nunca se hereda del Proxy.

### `lib/i18n` — las cadenas visibles van aquí, no en el JSX

```ts
import { t, tCon } from '@/lib/i18n';
t('armazon.cerrarSesion')                    // → 'Cerrar sesión'
tCon('clave.con.huecos', { nombre: 'Ana' })  // interpola {nombre}
```

El catálogo es `lib/i18n/es.ts`, un objeto anidado; las claves se escriben con puntos y
**el tipo las comprueba**: una clave que no existe no compila. Añade las tuyas ahí, en su
propia sección (p. ej. `acceso: { ... }`, `candado: { ... }`, `ajustes: { ... }`), y
devuelve `lib/i18n/es.ts` **entero**.

Hay una prueba que falla si dejas literales visibles en el JSX. Los `console.error` y los
`throw` internos **no** van al catálogo: los lee quien depura, no un usuario.

## Tareas

- [ ] **Pantalla de invitación** (solo administrador): nombre, correo, rol, y `centroId`
      **obligatorio si el rol es técnico administrativo** — el mismo `.refine` de
      `esquemaInvitacion` en cliente y en la acción. Llama a `invitarPerfil()`. La
      aplicación **no envía correo**: lo hace Supabase Auth, y en desarrollo se lee en
      Mailpit.
- [ ] **Primer acceso, en este orden exacto y sin atajos**: contraseña → TOTP (enroll +
      QR + verify + `generarCodigosRecuperacion()`, mostrados **una sola vez**) → PIN
      (`fijarPinHistoria()`), **salvo el técnico administrativo, que no ve el paso del
      PIN**. Quien decide en qué paso está cada usuario es `estadoDeCuenta()`; ningún
      componente lo decide por su cuenta.
- [ ] **Guardia del grupo `app/(app)/`**: un usuario con TOTP sin verificar no alcanza
      ninguna ruta del grupo — redirige al paso pendiente. Se comprueba con
      `estadoDeCuenta()` **y** con el nivel de autenticación real de la sesión
      (`supabase.auth.mfa.getAuthenticatorAssuranceLevel()` o lo que exponga la versión
      instalada de `@supabase/supabase-js`; **si no puedes comprobar la firma, dilo en
      FALTA**), no solo con el estado de la base.
- [ ] **Pantalla del candado del PIN**: pedirlo al abrir una historia
      (`desbloquearHistoria()`), botón de bloquear **siempre visible**
      (`bloquearHistoria()`), aviso **no modal** cuando la ventana va a caducar, y
      `prolongarDesbloqueo()` **solo en acciones reales del usuario, nunca al renderizar**.
- [ ] **Pantalla de PIN bloqueado por intentos**, con el tiempo restante hasta
      `bloqueadoHasta`. **Ni reintentos silenciosos, ni un mensaje que distinga «PIN
      incorrecto» de «ya estabas bloqueado»**: la base ya iguala las dos cosas a
      propósito; que la pantalla no las vuelva a separar.
- [ ] **Ajustes › reponer TOTP** (solo administrador, sobre OTRO perfil): `reponerTotp()`.
      **Reponer el PIN de otro NO EXISTE**: ni botón, ni ruta, ni acción. Si lo escribes,
      es un hallazgo, no una función.
- [ ] **Ajustes › baja de un perfil** (solo administrador): `darDeBajaPerfil()`. Si la
      base la rechaza por ser el último administrador activo, la pantalla **enseña el
      mensaje que ya trae `{ok:false, mensaje}`**; no lo previene adivinando cuántos
      administradores quedan.
- [ ] **Canje de código de recuperación**: `canjearCodigoRecuperacion()`. Con
      `motivo === 'ok'` el factor TOTP ya se borró: lleva al usuario a **reenrolar TOTP de
      inmediato**.
- [ ] **Sesión de 30 minutos de inactividad**, y comprueba que el botón de cerrar sesión
      de la barra lateral sigue funcionando.

## Criterios de aceptación

- [ ] **Automático** — `npm run lint`, `npm run build` y `npm test` limpios. Pega la
      salida real.
- [ ] **Automático** — un usuario invitado que no ha completado TOTP no alcanza ninguna
      ruta de `app/(app)/`: redirige al paso pendiente.
- [ ] **Automático** — un `profesional_sanitario` sin PIN va al alta de PIN; un
      `tecnico_administrativo` **no ve esa pantalla en absoluto**.
- [ ] **Automático** — invitar a un técnico administrativo sin centro falla en el
      formulario **antes** de llamar a `invitarPerfil()`.
- [ ] **Automático** — ninguna acción de renderizado llama a `prolongarDesbloqueo()`.
- [ ] **Manual** — con cada rol, la pantalla enseña exactamente lo que le concede la
      matriz de roles: el técnico no ve **nada** de PIN; el profesional no ve **nada** de
      invitaciones ni de bajas.
- [ ] **Manual** — buscar en la interfaz una forma de reponer el PIN de otro: no existe
      ningún camino, ni siquiera oculto.
- [ ] **Manual** — a 360 px de ancho todas las pantallas nuevas siguen usables.

## Reglas que se comprueban al revisar

1. **`redirect` siempre FUERA del `try`.** Dentro, Next lo captura como error.
2. **Un instante crudo no baja al navegador ya formateado por el navegador**: nada de
   `new Date()` en cliente para pintar horas.
3. **Ni un literal visible en el JSX**: todo por `t()`/`tCon()`.
4. **No inventes**. Si necesitas una función de `lib/cuentas/` que no está en la lista de
   arriba, no existe: dilo en FALTA.
5. **No integres nada** y no escribas en `docs/` ni en `tickets/`.
